执行顺序示例（本次已按相同流程完成）
--------------------------------
先从已推送的dshanpi/t153-openwrt取得最终固定commit，确认HEAD等于验收
commit后再做下面准备。SOURCE_ROOT为现有工程，VERIFY_ROOT为干净新checkout；
二者必须是不同的明确绝对路径，且新checkout内没有既有build_dir/staging。
以下变量只引用这两个工程，不会改变原Tina SDK：

  SOURCE_ROOT=/home/ubuntu/T153MX/T153_Tina_V1.0/openwrt25
  VERIFY_ROOT=/absolute/path/to/the/frozen-validation-checkout
  test "$SOURCE_ROOT" != "$VERIFY_ROOT"
  test ! -e "$VERIFY_ROOT/openwrt"
  test ! -e "$VERIFY_ROOT/downloads"
  ln -s "$SOURCE_ROOT/downloads" "$VERIFY_ROOT/downloads"
  (cd "$VERIFY_ROOT" && sh scripts/prepare-source.sh)
  test ! -e "$VERIFY_ROOT/openwrt/dl"
  ln -s "$SOURCE_ROOT/openwrt/dl" "$VERIFY_ROOT/openwrt/dl"

  cd "$VERIFY_ROOT"
  bash scripts/build-release.sh --jobs 4 --with-fes \
    --factory-image /home/ubuntu/T153MX/T153_Tina_V1.0/out/t153_linux_omnigate_uart0-default.img

build-release默认拒绝已存在的目标build树，最终验收不可加--incremental。
FES纯Python流程只读取同一份1.2GB原厂镜像，不复制到新checkout，也不调用SDK host工具。
如验收还需重新构建RAM引导辅助工具，完整OpenWrt结束后运行：
  python3 scripts/build-kexec-tools.py
它复用新checkout刚编出的工具链；下载归档来自共享downloads，目标输出独立。

完整构建通过后，按同一commit生成的manifest重新做FES烧录、重启整盘SHA、
Linux/rootfs和网络验收；不得用之前增量生成的固件替换这轮产物。
保存新checkout的logs/rebuild-*和最终实机记录，核实后再决定是否删除验证构建物。
