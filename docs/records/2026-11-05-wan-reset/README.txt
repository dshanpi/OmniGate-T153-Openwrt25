2026-11-05 RTL8211F 复位等待对照记录
===================================
说明与源码依据：../../WAN-RTL8211F-RESET.txt

runtime-validation.json记录镜像/FIT绑定、唯一RAM DT变化、三轮150ms传输
及匹配30ms对照。reset150-boot1/2/3.log为三轮完整串口记录。
matched-reset30.log复现能力缓存异常，但该短窗口没有掉线；不能把它称为
每次必掉线的负对照。upload-boot2.jsonl为构建主机独立接收并计算SHA的记录。

baseline-reboot.log、pause-ab.log、loopback-probe.log保留发现复位等待问题前
的上下文；暂停流控并非已经确认的修复，loopback-probe只检查状态，没有进行
AF_PACKET包回环。正式发布镜像尚需单独烧录和验证，本目录不是新镜像验收。

provenance.json保存串口原始及公开副本SHA256。公开副本规范化换行和ANSI，
用BUILD_HOST/WAN_MAC代替构建主机地址与板卡MAC。板卡RTC未校准，时间判断
以启动日志的相对秒数为准。原始文件保留在调试工作区，不覆盖历史记录。

更新：恢复150ms的第四次启动在约18分钟空闲窗口内仍出现3次WAN down/up，
carrier_changes=7，检查时恢复1G。用户确认只接EC20，未动网线/交换机。
该轮完整串口记录已归档为restored150.log；runtime-validation.json
明确区分前三轮传输通过与第四轮稳定性失败。150ms能力时序修正并未解决全部掉线。

后续集成 RAM 更新：连接功能 RAM 在约1089秒掉线并降100M；UART FIFO/AFCE
修复 RAM 又出现多次掉线，清除标准 EEE 广告并读回确认后，在572.964061秒
再次自然掉线、584.406861秒恢复100M。因此150ms与关闭EEE广告均未解决WAN
稳定性。runtime-validation.json 的 later_ram_trials 单独记录新 FIT 与时间线，
不扩大原三轮272MiB/64MiB验收范围。完整说明见../../WAN-RTL8211F-RESET.txt。
UART/EEE末尾原始记录由板级任务继续补入../2026-11-05-connectivity/，当前
结构化摘要明确标记部分日志已上传、末尾事件来源为板级报告；不能用部分日志
hash冒充完整原始证据。人工重协商的380.564077秒down已与自然掉线分开。

用户后续确认：首轮f6259f61...连接功能RAM在多次SDIO恢复/EIR诊断后发生的
完整重启不是手动操作（“没有，板子一直没动”）。该次升级为已确认非人工
意外重启；串口未捕获明确panic原因，根因未知，不归咎SMP/DDR/AIC/供电。
更早用户确认手动的两次重启是不同事件。UART修复版raw7c777beb...已完成
FES及整盘SHA读回一致，不能据此宣称意外重启已修复或长期稳定。用户进一步
确认Tina稳定千兆时也插着同一块EC20；对照为同板同线同对端同EC20，不能
简单归因EC20接入或供电。RGMII延迟、150ms和EEE关闭均未根治主线掉线/降速。

PHY-mode EEE单变量对照收尾：本轮eMMC从100M起，仅a43:19 bit5由0843置0863，
648.244766秒人工重协商down，660.739997秒仍100M；约790秒0863读回确认。
没有恢复千兆，未产生1G稳定窗口。约898秒已恢复0843并读回，本次临时改动
已撤销，无新增永久WAN参数。源日志wan-phy-mode-eee-raw-20261105.log仍待
板级任务上传，结构化记录已明确证据来源/待归档边界。后续r2蓝牙停止清理
修复不等于WAN掉线或已确认非人工意外重启问题得到解决。
