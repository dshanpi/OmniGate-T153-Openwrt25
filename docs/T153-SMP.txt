T153 四核 Cortex-A7 源码适配（2026-11-05）
========================================

范围与状态
----------
本方案以 U-Boot 2026.07、OpenWrt openwrt-25.12 / Linux 6.12 的现有
T153 板级移植为基础。使用源码 SPL、源码 DDR4 初始化、源码 ARMv7 PSCI
monitor；不链接厂商 DDR 库或厂商多核 monitor。属于仓库外置板级补丁，
不能据此声称 T153 已合入上游官方 U-Boot / Linux。

软件检查及ad406a版本的首轮四核实机短测已通过：包含烧录/读回、四核上线、
调度/共享数据短测、普通重启和软件进入FEL；网络稳定性仍有问题。实机证据
另存于records/2026-11-05-smp-bringup/，不把ELF/DT检查当成硬件结果。
本配置启用 CPU0..CPU3，物理 DDR 1GiB，Linux 仍为
384MiB；扩展 Linux 内存并不在此次四核改动内。

多核启动架构
------------
CPU0 从 eMMC/SD 的 SPL 完成 DDR 后进入 U-Boot；U-Boot 在跳转 Linux 前
把主线 ARMv7 monitor 和 T153 CPU_ON 后端复制到固定 SRAM。
Linux 通过 PSCI 0.1 SMC CPU_ON 启动另外三个 Cortex-A7 核心。

  GIC：0x03400000
  SRAM C 已知物理范围：0x40000..0x67fff（160KiB）
  monitor 保留范围：0x50000..0x57fff（32KiB）
  FEL thunk / swap：0x66a00..0x67fff（不与 monitor 重叠）
  四个 monitor 栈：每核 1KiB，沿用主线 ARMv7 框架

monitor 运行时代码、数据、分派表、调用目标与栈均留在上述 SRAM。
SPL 已完成后才复制 monitor，因此与已退出的 SPL SRAM 占用不冲突。
没有假设或伪造 TrustZone 保护寄存器；SRAM 驻留不表示已配置硬件隔离。

CPU_ON 寄存器来源为 GPL SyterKit 的固定版本示例：
https://github.com/YuzukiHD/SyterKit/tree/7f539e17762639589897db835e58dd638b2bea80/boards/tlt153-minievm/app_sram/smp

  CPU 入口：0x07050070 + cpu * 4
  CPU power status：0x07051050 + cpu * 4
  CPU config：0x07051070 + cpu * 4（IRQ mask bit4）
  hotplug：0x07051080 + cpu * 4（wakeup bit0、request bit16）
  CPUIDLE enable：0x07051100，keys 0x16aa0000 / 0xaa160001
  延迟寄存器：0x07051140、0x07051144，各为24

只接受 CPU0 发起对 CPU1..3 的 CPU_ON。发起方与次级 CPU 使用有界
ready/release 握手；若调用超时，迟到的次级核留在 SRAM 等待，不能继续
访问已失效的临时 U-Boot DRAM。入口要求 MMU/D-cache 已关闭，否则停驻；
同时屏蔽 IRQ/FIQ，清理 I-cache/分支预测，沿用主线 psci_cpu_entry 设置 ACTLR.SMP、GIC、
monitor 栈与 nonsecure Linux 入口。CONFIG_ARMV7_SET_CORTEX_SMPEN 是
隐藏配置，由板级 Kconfig select，不能仅在 defconfig 写一行。

最终 DT 与限制
-------------
board fixup 在 arch_fixup_fdt 后执行，重建 /psci 为：
  compatible = "arm,psci"
  method = "smc"
  cpu_on = <0x95c1ba60>
CPU0..3 的 status="okay"、enable-method="psci"；添加 SRAM memreserve。
拒绝缺失、重复或越界 CPU ID，保留重复执行时的幂等性。

没有提供 cpu_off、cpu_suspend、migrate DT 属性，不宣称 PSCI 1.0。
CPU 热插拔、suspend、多核 kexec 均不支持。Linux watchdog 正常重启
使用 smp_send_stop，不依赖 CPU_OFF。四核启动验证不能用 multicore kexec。

早期 SPL 消费 RTC FEL 请求
------------------------
此前 Linux / U-Boot 写 RTC magic 并触发 watchdog 后仍重新正常启动。
原因是 T153 由 boot0 消费该请求，BootROM 不直接消费；源码 SPL 原先没有
对应处理。新代码在 console/timer 初始化后、DDR 初始化前检查：
  SRAM 0x40000 的 header magic 必须为 eGON.BT0；media 必须为0或2；
  RTC data2 0x07090108 必须等于 0x5aa5a55a。

清零步骤最多1000轮，每轮 write0 -> DSB -> ISB -> readback。
只有成功读到0才跳转；失败停在 SRAM，不带着未清 magic 反复回 BootROM。
随后屏蔽 IRQ/FIQ，按24MHz CNTPCT 等100us，清 SCTLR 的 I/C/A/M，
失效 I-cache 和分支预测，DSB/ISB，再等10ms，进入 ARM physical 0x20。

物理入口和清理序列来自原SDK只读参考：
  device/config/chips/t153/bin/boot0_sdcard_sun8iw22p1.bin
  SHA256 b2fad4436c32d0c9b1c9607532835df9db411489819763879eab73a4f97127dd
  cold flow：0x4d6ea -> flag read0x43a04 -> clear0x43a7c
  cache cleanup：0x4215e；100us counter delay：0x420a0
  10ms：0x420c4；ARM entry32 jump helper：0x42198
  clear helper 0x439e8..0x43a02：write0、barrier、read，原版无界重试

额外恢复 save_boot_params 保存的原始 VBAR，是为了补偿主线 start.S
会修改 VBAR 而厂商 boot0 不修改的差异；不是声称厂商反汇编原本就有此步。
此路径是新启动 BootROM FEL，不恢复旧 SP/LR/CPSR。
eGON.FEL USB 加载路径仍使用原 t153_return_to_fel 保存上下文返回，保持独立。
