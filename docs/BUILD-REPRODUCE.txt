二、构建主机
------------

Python 3、device-tree-compiler、u-boot-tools、e2fsprogs、dosfstools、
mtools及libusb-1.0开发包；ddr/ARM模型分析另用pyelftools、Unicorn。
Ubuntu 24.04依赖安装命令（仅安装主机依赖，不访问板卡）：

三、当前1GiB源码构建路径（已审查入口，最终干净复跑待执行）
----------------------------------------------------------
新统一入口（已通过语法、依赖及干净目录保护检查；完整执行尚待最终复跑）：
  bash scripts/build-release.sh --jobs 4
同时复现FES，提供用户拥有的原厂镜像：
  bash scripts/build-release.sh --jobs 4 --with-fes --factory-image /path/to/factory.img
默认拒绝已有build_dir/staging_dir/tmp/bin/.config及1g U-Boot目标目录；
最终验收使用干净目录。开发增量才用--incremental。
每步日志/exit和最终软件build-report保存在logs/rebuild-*，不访问USB或自动烧板。
以下是同一流程的底层入口，均在仓库根目录执行：
  mkdir -p logs
  sh scripts/prepare-source.sh
  JOBS=4 sh scripts/build.sh "$PWD/openwrt"
  JOBS=4 sh scripts/build-uboot-source-1g.sh
  python3 scripts/package-uboot-source-1g.py
  sh scripts/package-artifacts.sh "$PWD/openwrt" --openwrt-only
  python3 scripts/package-disk-image.py --profile 1g
  python3 scripts/package-disk-image.py --profile 1g --verify-only

OpenWrt配置入口configs/t153mx-omnigate.config，经make defconfig展开。
1GiB板的U-Boot入口dshanpi_t153_source_1g_defconfig。
不要将512MiB默认profile或旧RAM-chainload目标代入本板冷启动镜像。
本次整盘输入是普通FIT+ext4 rootfs；initramfs FIT为独立RAM验证用途。
新build-release.sh已显式串联1g/FES步骤并在最后刷新SHA256SUMS；
旧package-artifacts.sh单独调用仍不足以完成1g流程。硬件验收记录独立保存，
不能让软件脚本输出“烧录或运行成功”。

四、软件检查
------------
  sh scripts/test-ddr-source.sh

其余旧FEL安装器及ARM仿真测试仍属512MiB实验profile，不作为1g入口依赖。
package-artifacts的--openwrt-only跳过旧RAM/512目标的条件打包；统一入口
显式构建1g核心，不依赖旧产物、FEL安装器或kexec工具。
不能只读取源码来证明修复进入镜像：应解出FIT实际内核/DT核对符号及代码，

五、FES构建/烧录复现
------------------------
当前有效RAM临时loader为t153-fes-ddr933-ram-loader.img；它使用厂商
FES1 DDR二进制，持久镜像中的DDR/SPL/U-Boot则全部来自本工程源码。
不能将“主线持久固件全部源码”扩写成“整个FES临时loader全部源码”。
prepare-fes-stock.py已能直接从SHA锁定的用户原厂镜像提取六payload并重建
stock RAM容器；package-fes-ddr933.py再用纯Python修改频率和eGON checksum。
无需update_fes1、dragon、T113本地目录或SDK中的主机可执行文件。
在仅有两脚本和三JSON元数据的隔离目录实跑，与两个原候选逐字节一致。
详见FES-REPRODUCE.txt和logs/fes-portable-reproduction-audit.json。
厂商二进制仍由用户供给，许可标LicenseRef-NOASSERTION，不放入源码仓库；
源码化的是提取、组包、参数修改和验证过程，不能冒充FES1 DDR源码。

raw写盘地址须使用当前OpenixCLI/MCP的stock映射：主机已补偿+40960扇区，
保留loader原MMC偏移；不要使用已禁用physical0 loader再做一次抵消。
通用MCP完整JSON请求、下载/任务轮询与结果判据已在host-tools/README.txt
及mcp-fes-workflow.example.json中提供，无私人会话。完整步骤见FLASH-SOURCE.txt。
工具当前版本/能力以连接时capabilities为准；原生回FEL实机验证尚待重连。
